Real-Time Audio DSP in the Browser: Compiling SoundTouch and RubberBand to WebAssembly

Nov 15, 2026 • 12 min read • By HashGANG Insights

Learn how to compile C++ digital signal processing libraries into WebAssembly (Wasm) and execute audio pitch/tempo shifting inside high-performance AudioWorklet threads without main-thread jitter.

1. Why Traditional JavaScript Audio Processing Fails at Scale

Real-time digital signal processing (DSP)—such as modifying vocal pitch for privacy, time-stretching audio without pitch distortion, or applying dynamic spatial filters—demands deterministic sub-15ms computation cycles. Historically, web developers attempted to process PCM audio buffers using the deprecated ScriptProcessorNode in JavaScript.

However, JavaScript running on the browser's main UI thread is subject to asynchronous event loops, DOM layout reflows, and unpredictable V8 garbage collection (GC) pauses. A single 20ms GC pause causes an audio buffer underrun, producing audible clicks, pops, and stuttering that destroy voice intelligibility.

Modern browser audio engineering solves this through a two-pillar architecture: the Web Audio API AudioWorklet thread combined with WebAssembly (Wasm) compiled native C++ DSP engines.

2. Compiling C++ SoundTouch & RubberBand with Emscripten

SoundTouch and RubberBand are industry-standard native C++ algorithms for pitch shifting and tempo modification. SoundTouch uses the WSOLA (Waveform Similarity Overlap-Add) algorithm in the time domain, while RubberBand employs phase vocoder techniques in the frequency domain.

To run these high-performance libraries inside the browser, we compile the source code using Emscripten with SIMD (Single Instruction, Multiple Data) optimizations enabled:

# Emscripten compile command for SoundTouch WebAssembly module
emcc -O3 -msimd128   -s WASM=1   -s ENVIRONMENT='web,worker'   -s ALLOW_MEMORY_GROWTH=1   -s EXPORTED_FUNCTIONS='["_soundtouch_create", "_soundtouch_setPitchSemiTones", "_soundtouch_putSamples", "_soundtouch_receiveSamples", "_soundtouch_destroy"]'   -s EXPORTED_RUNTIME_METHODS='["ccall", "cwrap", "HEAPF32"]'   -I ./include   source/SoundTouch.cpp source/TDStretch.cpp source/RateTransposer.cpp   -o dist/soundtouch.js

Key compiler flags explained:

  • -msimd128: Leverages modern 128-bit vector CPU registers in Chrome and Safari, quadrupling float32 audio arithmetic throughput.
  • -s ENVIRONMENT='web,worker': Ensures the compiled glue code contains zero DOM or window references, enabling direct instantiation inside dedicated AudioWorklet threads.
  • -O3: Enables full LLVM loop unrolling, vectorization, and dead-code elimination.

3. Bridging AudioWorkletProcessor and the Wasm Linear Memory Heap

The AudioWorkletProcessor runs inside a dedicated real-time audio rendering thread with elevated operating system priority. Every 128 audio samples (approx. 2.9ms at 44.1kHz), the browser invokes the process(inputs, outputs, parameters) callback.

// soundtouch-processor.js - Runs inside AudioWorkletGlobalScope
class PitchShiftProcessor extends AudioWorkletProcessor {
  constructor(options) {
    super();
    this.wasmInstance = options.processorOptions.wasmInstance;
    this.soundTouchPtr = this.wasmInstance._soundtouch_create();
    this.wasmInstance._soundtouch_setPitchSemiTones(this.soundTouchPtr, -4.0); // Deep voice effect
    this.inputBufferPtr = this.wasmInstance._malloc(128 * 4); // float32 buffer
    this.outputBufferPtr = this.wasmInstance._malloc(512 * 4);
  }

  process(inputs, outputs, parameters) {
    const input = inputs[0];
    const output = outputs[0];
    if (!input || !input[0]) return true;

    const inputChannel = input[0];
    // Copy input samples directly into Wasm linear memory heap
    this.wasmInstance.HEAPF32.set(inputChannel, this.inputBufferPtr / 4);

    // Feed samples into SoundTouch DSP pipeline
    this.wasmInstance._soundtouch_putSamples(this.soundTouchPtr, this.inputBufferPtr, 128);

    // Retrieve pitch-shifted output samples
    const samplesReceived = this.wasmInstance._soundtouch_receiveSamples(
      this.soundTouchPtr,
      this.outputBufferPtr,
      128
    );

    if (samplesReceived > 0) {
      const shifted = this.wasmInstance.HEAPF32.subarray(
        this.outputBufferPtr / 4,
        (this.outputBufferPtr / 4) + samplesReceived
      );
      output[0].set(shifted);
    }

    return true;
  }
}

registerProcessor('pitch-shift-processor', PitchShiftProcessor);

4. Achieving Zero-Memory Allocation in Hot Audio Loops

The cardinal rule of audio DSP programming is: Never allocate or deallocate memory inside the audio callback loop. Invoking new Float32Array(), malloc(), or object literals within process() triggers garbage collection runs that stall the audio thread.

By pre-allocating circular ring buffers in the Wasm linear heap during processor construction and utilizing typed array views (subarray()) rather than copies, the audio pipeline achieves zero allocations per tick, maintaining an unwavering 0% packet loss and rock-solid 60 FPS UI responsiveness.

Conclusion: Enterprise Privacy via Browser-Native Audio DSP

Bringing native C++ DSP libraries into the browser via WebAssembly empowers platforms to provide anonymous voice filters, real-time noise suppression, and dynamic acoustics locally on client devices—guaranteeing 100% end-to-end privacy with zero server compute overhead.
